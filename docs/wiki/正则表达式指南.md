# 正则表达式指南（贡献者必读）

**简体中文** | [English](#regular-expression-guide-required-reading-for-contributors-english)

加载器用 C++ `std::regex`（ECMAScript 语法）对 `main.js` / `renderer.js` 全文做查找替换。写映射条目前请通读本文——多数「匹配不到」或「汉化后打不开」的问题都源于没吃透转义规则。

## 1. 转义总规则

查找项（正则）与替换项（字面量）的转义规则**完全不同**：

| 字符 | 查找项（正则） | 替换项（字面量） |
| --- | --- | --- |
| 双引号 `"` | 一个反斜杠：`\"` | 一个反斜杠：`\"` |
| 正则特殊字符（`. * + ? ( ) [ ] { } ^ $ \| \ /`） | **两个**反斜杠：`\\(` | **零个**反斜杠：`(` |
| `$`（捕获组引用除外） | `\\$` | `$$`（避免 format 串展开，少见） |
| `\` 字面量 | `\\\\`（JSON 两层 + 正则一层） | 不需要 |

> 记忆法：查找项里「为正则而加的反斜杠」在 JSON 里都要**双写**；只有双引号因为属于 JSON 语法，只需单写一个反斜杠。替换项是**字面量**，为正则加的反斜杠一律不要。

### 对错对照

匹配含双引号的文本（`i am "zhangsan"`）：

- 错误：`['i am "zhangsan"','我是"张三"']`（最外层用单引号、内层双引号不转义——**不允许**）
- 正确：`["i am \"zhangsan\"","我是\"张三\""]`

匹配 `?` 字符本身：查找项写 `\\?`（JSON 双反斜杠 → 正则 `\?`）；替换项直接写 `?`，前面**不要**反斜杠。

## 2. 查找项书写建议

### 带上引号，避免误匹配

打包后的 js 里字符串以 `"..."` 形式内联，查找项建议带引号边界：

```json
["\"&View\"", "\"视图(&V)\""]
```

不带引号时 `&View` 会先命中 `&View on GitHub` 之类更长文本，把它改坏后，本应匹配那些长文本的映射就再也匹配不到了（连锁失效）。

### 用正则模糊匹配易变片段

打包变量名（两位字符的组件名/函数名）几乎每个版本都变：

```json
["Ee\\.createElement\\((..),null,this.props.repositoryName",
 "Ee.createElement($1,null,this.props.repositoryName"]
```

- 查找：`\\(`（JSON 双反斜杠 → 正则 `\(`），`(..)` 捕获任意两位字符；
- 替换：`$1` 回填捕获内容——替换项是 `std::regex_replace` 的 format 串，`$1` 表示第一个捕获组；
- **替换项绝不写 `\\(`**：那是字面反斜杠，写入 js 后 `createElement\(` 直接语法报错、GitHub Desktop 打不开。

### 复杂动态文本用三元素 `#{n}` 回填

查找正则自身捕获不够用时，第三项在全文找首个匹配回填占位符，详见[映射文件格式](映射文件格式.md#n-占位符回填机制)。

## 3. `std::regex` 兼容性黑名单（CI 强制）

查找正则由 **C++ `std::regex`** 编译执行——不是 JS 正则！以下语法在 JS 里合法，但 `std::regex` **不支持**，写了会让加载器抛 `regex_error`（触发整文件中止回滚）。CI 质量门会对这些语法直接报错：

| 语法 | 名称 | 后果 |
| --- | --- | --- |
| `(?<=…)`, `(?<!…)` | 后行/后顾断言 | `std::regex` 编译失败 |
| `(?<name>…)` | 命名捕获组 | 编译失败（仅支持匿名捕获组） |
| `\p{…}`, `\P{…}` | Unicode 属性类 | 编译失败 |
| `(?i)` 等内联 flag | 内联修饰符 | 编译失败 |
| `\d` `\w` 等字符类之外的 JS 扩展 | — | 部分支持，以 `std::regex` ECMAScript 方言为准 |

> 经验：写完正则在 [regex101](https://regex101.com/) 选 **ECMAScript** 方言验证，或直接跑加载器的 `--invalidcheck`（见第 5 节）。

### ReDoS 防护

CI 还带 ReDoS 启发式检查：嵌套量词（如 `(a+)+`）、重叠交替加量词等灾难性回溯模式会被拦截。查找项面向的是固定 js 文本而非恶意输入，风险主要是「替换巨慢」而非攻击，但同样不要写。

## 4. 条目顺序（「短含长」）

查找**按数组顺序逐条执行，先匹配者生效**：

- 例：已有条目 `"Save"`（短、宽泛），新条目 `"Save":"Add"`（长、具体，是前者的子串）；
- 若短条目在前：`"Save"` 先把 `"Save":"Add"` 里的 `Save` 改掉 → 长条目永远匹配不到；
- **必须把长（具体）条目插在短（宽泛）条目之前**；
- 不存在包含关系的新条目一律**追加到数组末尾**即可；
- CI 质量校验会对错误的相对顺序告警，但请提交前自查。

## 5. 提交前自检

```powershell
# 批量检测失效条目（匹配不到 / 正则非法）
# --translationfrombak：以未汉化的干净备份为底稿，避免已汉化文本干扰
GitHubDesktop2Chinese.exe --nopause dev --invalidcheck --translationfrombak
```

- 退出码 = 失效条数（0 为全部有效）；
- 或用 Node.js 自动维护工具（还能顺带提取未翻译候选）：

  ```bash
  cd tools/auto-maintain && npm run all
  ```

  报告位于系统临时目录 `ghdesktop-auto-maintain/report.md`，详见[自动维护工具](自动维护工具.md)。

## 6. 译文风格

- 问句句末问号用**全角** `？`（CI 强制）；
- 译文末尾**不留空格**（CI 强制）；
- Windows 访问键写法：`文件(&F)`；
- 专有名词（Commit、Rebase、Stash、Fork 等社区通用词）保留英文原文；
- 与 GitHub 官方中文文档术语保持一致：repository→存储库、pull request→拉取请求、issue→议题。

## 7. 常用正则速查

| 符号 | 含义 |
| --- | --- |
| `.` | 任意单个字符（除换行） |
| `*` / `+` / `?` | 前一元素 0+ / 1+ / 0 或 1 次 |
| `{n}` / `{n,}` / `{n,m}` | 精确 n 次 / 至少 n 次 / n~m 次 |
| `^` / `$` | 输入串开始 / 结束 |
| `[…]` | 字符集 |
| `|` | 或 |
| `( )` | 捕获组（替换项用 `$1`… 引用） |
| `(?: )` | 非捕获组 |
| `\\.` | 字面量 `.`（JSON 转义后） |

> JSON 语法提醒：数组最后一项结尾**不可有逗号**；文件必须整体是合法 JSON，否则加载器解析失败直接退出。

# Regular Expression Guide (required reading for contributors) (English)

[简体中文](#正则表达式指南贡献者必读) | **English**

The loader uses C++ `std::regex` (ECMAScript syntax) to find-and-replace across the full text of `main.js` / `renderer.js`. Please read this page through before writing mapping entries — most "no match found" or "GitHub Desktop won't open after localizing" problems stem from not fully digesting the escaping rules.

## 1. The Master Escaping Rules

The escaping rules for the find item (a regex) and the replacement item (a literal) are **completely different**:

| Character | Find item (regex) | Replacement item (literal) |
| --- | --- | --- |
| Double quote `"` | One backslash: `\"` | One backslash: `\"` |
| Regex special characters (`. * + ? ( ) [ ] { } ^ $ \| \ /`) | **Two** backslashes: `\\(` | **Zero** backslashes: `(` |
| `$` (except capture-group references) | `\\$` | `$$` (avoids format-string expansion; rare) |
| A literal `\` | `\\\\` (two JSON layers + one regex layer) | Not needed |

> Memory aid: in the find item, every backslash added *for regex purposes* must be **doubled** in JSON; only the double quote, being part of JSON syntax itself, takes a single backslash. The replacement item is a **literal** — never include backslashes added for regex purposes.

### Right vs. Wrong

Matching text that contains double quotes (`i am "zhangsan"`):

- Wrong: `['i am "zhangsan"','我是"张三"']` (outer single quotes with unescaped inner double quotes — **not allowed**)
- Correct: `["i am \"zhangsan\"","我是\"张三\""]`

Matching the `?` character itself: write `\\?` in the find item (JSON double backslash → regex `\?`); write plain `?` in the replacement, **without** a preceding backslash.

## 2. Tips for Writing Find Patterns

### Include the quotes to avoid false matches

Strings are inlined as `"..."` in the bundled js, so find patterns should carry quote boundaries:

```json
["\"&View\"", "\"视图(&V)\""]
```

Without the quotes, `&View` matches the `&View` inside longer text like `&View on GitHub` first; once that longer text is corrupted, the mappings that were supposed to match it can never match again (cascading invalidation).

### Fuzzy-match volatile fragments with regex

Bundled variable names (two-character component/function names) change almost every release:

```json
["Ee\\.createElement\\((..),null,this.props.repositoryName",
 "Ee.createElement($1,null,this.props.repositoryName"]
```

- Find: `\\(` (JSON double backslash → regex `\(`), and `(..)` captures any two characters;
- Replace: `$1` backfills the captured content — the replacement is a `std::regex_replace` format string, where `$1` means the first capture group;
- **Never write `\\(` in the replacement**: that is a literal backslash; once written into the js, `createElement\(` is an immediate syntax error and GitHub Desktop won't open.

### Use the three-element `#{n}` backfill for complex dynamic text

When the find regex's own captures aren't enough, the third element finds the first full-text match and backfills the placeholders; see [Mapping File Format](映射文件格式.md#n-占位符回填机制).

## 3. The `std::regex` Compatibility Blacklist (CI-Enforced)

Find patterns are compiled and executed by **C++ `std::regex`** — not a JS regex! The following syntax is legal in JS but **unsupported** by `std::regex`; using it makes the loader throw `regex_error` (which triggers a whole-file abort and rollback). The CI quality gate rejects these outright:

| Syntax | Name | Consequence |
| --- | --- | --- |
| `(?<=…)`, `(?<!…)` | Lookbehind (positive/negative) assertions | `std::regex` fails to compile |
| `(?<name>…)` | Named capture groups | Fails to compile (only unnamed capture groups are supported) |
| `\p{…}`, `\P{…}` | Unicode property classes | Fails to compile |
| `(?i)` and other inline flags | Inline modifiers | Fails to compile |
| JS extensions beyond character classes like `\d` `\w` | — | Partially supported; the `std::regex` ECMAScript dialect is authoritative |

> Tip: after writing a regex, verify it on [regex101](https://regex101.com/) with the **ECMAScript** flavor selected, or simply run the loader's `--invalidcheck` (see Section 5).

### ReDoS Protection

CI also runs a heuristic ReDoS check: nested quantifiers (e.g. `(a+)+`), overlapping alternation combined with quantifiers, and other catastrophic-backtracking patterns are rejected. Find patterns target fixed js text rather than hostile input, so the risk is mainly "the replacement becomes extremely slow" rather than an attack — but still, don't write them.

## 4. Entry Order ("Short-in-Long")

Find patterns **run one by one in array order; the first match wins**:

- Example: existing entry `"Save"` (short, broad), new entry `"Save":"Add"` (long, specific, a substring of the former);
- If the short entry comes first: `"Save"` rewrites the `Save` inside `"Save":"Add"` → the long entry can never match;
- **The long (specific) entry must be inserted before the short (broad) one**;
- New entries with no containment relationship can simply be **appended at the end**;
- The CI quality check warns about wrong relative order, but please self-review before submitting.

## 5. Pre-Submission Self-Check

```powershell
# 批量检测失效条目（匹配不到 / 正则非法）
# --translationfrombak：以未汉化的干净备份为底稿，避免已汉化文本干扰
GitHubDesktop2Chinese.exe --nopause dev --invalidcheck --translationfrombak
```

- Exit code = number of invalid entries (0 means all valid);
- Or use the Node.js auto-maintain tool (which also extracts untranslated candidates):

  ```bash
  cd tools/auto-maintain && npm run all
  ```

  The report lands in the system temp directory `ghdesktop-auto-maintain/report.md`; see the [Auto-Maintain Tool](自动维护工具.md) page.

## 6. Translation Style

- End questions with the **full-width** `？` (CI-enforced);
- **No trailing spaces** at the end of translations (CI-enforced);
- Windows access-key style: `文件(&F)`;
- Keep community-standard proper nouns (Commit, Rebase, Stash, Fork, etc.) in English;
- Stay consistent with GitHub's official Chinese documentation terminology: repository→存储库, pull request→拉取请求, issue→议题.

## 7. Common Regex Quick Reference

| Symbol | Meaning |
| --- | --- |
| `.` | Any single character (except newline) |
| `*` / `+` / `?` | Previous element 0+ / 1+ / 0 or 1 times |
| `{n}` / `{n,}` / `{n,m}` | Exactly n times / at least n / n to m times |
| `^` / `$` | Start / end of the input string |
| `[…]` | Character class |
| `|` | Or |
| `( )` | Capture group (referenced as `$1`… in the replacement) |
| `(?: )` | Non-capturing group |
| `\\.` | A literal `.` (after JSON escaping) |

> JSON syntax reminder: the last item of an array must **not** have a trailing comma; the file must be valid JSON as a whole, otherwise the loader aborts on parse failure.
