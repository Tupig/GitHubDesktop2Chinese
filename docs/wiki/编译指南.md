# 编译指南

**简体中文** | [English](#build-guide-english)

项目基于 **CMake ≥ 3.30 + C++20**，支持三套工具链：**MSVC（Windows）/ AppleClang（macOS）/ GCC（Linux）**。仅支持 **64 位**（x64 / arm64）构建，32 位会在 CMake 配置阶段直接 `FATAL_ERROR`。

```powershell
# 三平台通用
cmake -B build
cmake --build build --config Release
```

## 1. 环境准备

### Windows（MSVC + VS2022）

1. 安装 [Visual Studio 2022](https://visualstudio.microsoft.com/)，勾选「使用 C++ 的桌面开发」工作负载（含 CMake 组件与 Ninja）；
2. 无需预装 OpenSSL——预编译 x64 静态库随仓库提交在 `third_party/openssl/`（版本与本地重建方式见 [`third_party/README.md`](../../third_party/README.md)，另见第 3 节）；
3. 无需额外装 vcpkg / conan：所有第三方头文件与库都随仓库提交在 `third_party/`。

**方式 A：VS2022 直接打开（推荐日常开发）**

1. 克隆仓库；
2. VS2022 → 「打开 → 本地文件夹」选择仓库根目录（VS 通过 CMakePresets.json 自动识别）；
3. 配置下拉框选 `x64-debug` 或 `x64-release` 预设（Ninja 生成器，产物在 `out/build/<预设名>/`）。

**方式 B：命令行**

```powershell
cmake --preset x64-release          # 配置（Ninja, cl.exe）
cmake --build --preset x64-release  # 构建
```

> 命令行方式需在「Developer PowerShell for VS 2022」中执行，保证 `cl.exe` 与 Ninja 在 PATH。

### macOS（AppleClang）

```bash
# 依赖：Xcode Command Line Tools + CMake/Ninja（OpenSSL 静态库已内置 third_party，无需 brew 安装）
xcode-select --install
brew install cmake ninja

cmake -B build -G Ninja
cmake --build build
```

OpenSSL 3.5.9 静态库（`libssl.a` / `libcrypto.a`）已按架构内置提交于 `third_party/openssl-macos-{x64,arm64}`，CMake 按 `CMAKE_OSX_ARCHITECTURES`（回退系统架构）自动选目录并静态链接。本地构建与 CI 发布的 macOS 产物**按架构拆分**（`TuPigGHD2Chinese-macos-x64` / `-macos-arm64`）行为一致，均以 strip + LTO 裁剪体积（部署目标 macOS 11.0）。

### Linux（GCC）

```bash
sudo apt update
sudo apt install -y build-essential cmake ninja-build

cmake -B build -G Ninja
cmake --build build
```

OpenSSL 3.5.9 静态库（`libssl.a` / `libcrypto.a`，`-fPIC` 构建）已内置提交于 `third_party/openssl-linux-x64`，CMake 直接查找并静态链接，无需 `libssl-dev`。

## 2. CMake 配置要点

| 要点 | 说明 |
| --- | --- |
| 版本宏 | CI 通过 `-DFILE_VERSION=…` 注入版本号；本地构建默认 `0.0.0-Dev.0` → 开发者版本（debug 日志、跳过自更新、可用 `--devsetver`） |
| 64 位守卫 | `CMAKE_SIZEOF_VOID_P != 8` 直接报错；对 VS `-A x64` 与 Ninja 两条路径都生效 |
| MSVC 选项 | `/utf-8`（中文字符集）；Debug `/bigobj`；Release `/Zi` + `/DEBUG`（生成 PDB） |
| 清单 | 链接 `src/app.manifest` 声明进程级 UTF-8 主动代码页——缺失时非中文系统上中文路径参数会解析失败 |
| C++ 标准 | `CXX_STANDARD 20`（用到 `std::optional`、`string::ends_with` 等） |

## 3. OpenSSL 依赖（平台差异）

| 平台 | 来源 | 备注 |
| --- | --- | --- |
| Windows | `third_party/openssl/`（随仓库提交的 `libssl.lib` / `libcrypto.lib` + 头文件，由主工作流 vendor 任务从上游源码构建） | CMake 直接查找并链接，无需联网；库文件缺失时按 [`third_party/README.md`](../../third_party/README.md) 用 vendor 任务重建。可用 `-DGHD2C_OPENSSL_ROOT=<目录>` 覆盖头文件/库查找位置 |
| macOS | `third_party/openssl-macos-{x64,arm64}`（随仓库提交的 `libssl.a` / `libcrypto.a` + 头文件） | 按 `CMAKE_OSX_ARCHITECTURES`（回退系统架构）自动选目录并静态链接；缺失时 `git checkout -- third_party/openssl-macos-x64 third_party/openssl-macos-arm64` 恢复，或用 vendor 任务重建。可用 `-DGHD2C_OPENSSL_ROOT=<目录>` 覆盖 |
| Linux | `third_party/openssl-linux-x64`（随仓库提交的 `libssl.a` / `libcrypto.a` + 头文件，`-fPIC` 构建） | CMake 直接查找并静态链接（附 `CMAKE_DL_LIBS` 补齐 dlopen 依赖）；缺失时 `git checkout -- third_party/openssl-linux-x64` 恢复，或用 vendor 任务重建。可用 `-DGHD2C_OPENSSL_ROOT=<目录>` 覆盖 |

第三方头文件库（CLI11、cpp-httplib、nlohmann/json、spdlog、WinReg）全部 header-only，随仓库提交于 `third_party/include/`，无获取步骤。

## 4. 产物

| 平台 | 产物 | 位置 |
| --- | --- | --- |
| Windows | `TuPigGHD2Chinese.exe` | `out/build/x64-release/` 或 `build/` |
| macOS / Linux | `TuPigGHD2Chinese` | `build/` |

> Windows 本地构建依赖系统 VC++ 运行库（Release 动态链接 CRT），与发布产物行为一致。

## 5. 常见构建错误

| 现象 | 原因与处理 |
| --- | --- |
| `仅支持 64 位架构（x64/arm64）构建` | 用了 32 位工具链/预设。VS 里选 x64 预设；命令行配置加 `-A x64` 或用 `x64-*` 预设 |
| `cl.exe` 找不到 | 未在 VS 开发者终端中运行命令行构建；或仅装了 VS Code 未装 MSVC |
| `libssl.lib` / `libcrypto.lib` 不存在 | `third_party/openssl` 未签出或被误删。`git checkout -- third_party/openssl` 恢复；或按 [`third_party/README.md`](../../third_party/README.md) 用主工作流 vendor 任务重建 |
| CMake 版本过低报 `cmake_minimum_required` | 升级 CMake ≥ 3.30 |
| macOS/Linux `libssl.a` / `libcrypto.a` 不存在 | 内置库目录被误删。`git checkout -- third_party/openssl-macos-x64 third_party/openssl-macos-arm64 third_party/openssl-linux-x64` 恢复；或按 [`third_party/README.md`](../../third_party/README.md) 用 vendor 任务重建 |
| 中文注释编译报错（MSVC） | 已通过 `/utf-8` 处理；若自己新增编译选项勿移除该项 |

## 6. 构建后验证

```powershell
# 不写盘，仅批量检测映射有效性（退出码 0 = 全部有效）
./build/TuPigGHD2Chinese.exe --nopause dev --invalidcheck --translationfrombak

# 或用 Node 工具做同等检测 + 未翻译候选提取
cd tools/auto-maintain && npm run all
```

C++ 单元测试（`version_test` / `replace_engine_test` / `selfupdate_test`，用 GoogleTest 断言、CTest 聚合，改 `src/` 或 `tests/` 后必跑）：

```powershell
ctest --preset x64-release   # 等价于 ctest -C Release --output-on-failure
```

> 多配置生成器陷阱：`cmake -B build` 在 Windows 默认生成 VS 多配置目录，其中直接 `ctest` 不带 `-C Release` 会以 `Not Run` 假失败（#169）；preset 已内置该参数，推荐统一走 preset 入口。
> GoogleTest 随仓库提供（`third_party/googletest/`），构建期不下载。

工具链单元测试与覆盖率（改 `tools/` 下校验器或自动维护工具后必跑）：

```powershell
# Python 校验器测试 + 覆盖率门禁（pytest 收集 tools/ci 全部 *-test.py）
python -m pip install -r tools/ci/requirements-dev.txt
python -m pytest --cov --cov-report=term-missing --cov-fail-under=90

# Node 工具测试 + 覆盖率门禁（Vitest，阈值见 tools/auto-maintain/vitest.config.mjs）
cd tools/auto-maintain
npm ci
npm test

# C++ 覆盖率（Linux 上；Windows/MSVC 无本地覆盖率工具）
cmake -B build-cov -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS=--coverage -DCMAKE_EXE_LINKER_FLAGS=--coverage
cmake --build build-cov --target version_test replace_engine_test utils_test
./build-cov/version_test && ./build-cov/replace_engine_test && ./build-cov/utils_test
# 仅度量本仓被测头文件；须排除 third_party（vendored googletest 路径也含 /src/）
gcovr --root . --filter '.*/src/utils/.*' --filter '.*/src/version/.*' --exclude '.*/third_party/.*' --txt --fail-under-line 65
```

改动加载器逻辑时，建议配合 `main_dev` / `renderer_dev` 数组 + `--devreplace` 快速验证，参见[贡献指南](贡献指南.md)。

加载器改动的冒烟回归可用 [`tools/ci/smoke-test.ps1`](../../tools/ci/smoke-test.ps1)：自动探测构建产物，依次跑帮助、非法参数、临时目录汉化、回滚四组用例，全部 PASS 即通过。Windows PowerShell 5.1 与 pwsh 7 均可运行（#136：脚本已规避 5.1 下 stderr 重定向触发 `NativeCommandError` 中止的问题）。

## 7. 本地静态检查（LSP）配置

本地用 LSP/clangd 检查 `src/*.cpp` 时，若持续报 spdlog、nlohmann/json 等 third_party 头文件"找不到"，是本地未配置头文件搜索路径所致（CI 构建与质量门不受影响），导出编译数据库即可从根上消除：

```powershell
# CMake 配置时顺带导出 compile_commands.json（对构建无副作用）
cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

把 LSP 指向 `build/compile_commands.json`（clangd 用 `--compile-commands-dir=build` 或项目根 `.clangd` 配置；VS Code C/C++ 扩展用 `C_Cpp.default.compileCommands`）。该文件不入库，CI 亦不依赖。

# Build Guide (English)

[简体中文](#编译指南) | **English**

The project is built with **CMake ≥ 3.30 + C++20** and supports three toolchains: **MSVC (Windows) / AppleClang (macOS) / GCC (Linux)**. Only **64-bit** (x64 / arm64) builds are supported; a 32-bit configuration aborts at the CMake configure stage with `FATAL_ERROR`.

```powershell
# Works on all three platforms
cmake -B build
cmake --build build --config Release
```

## 1. Prerequisites

### Windows (MSVC + VS2022)

1. Install [Visual Studio 2022](https://visualstudio.microsoft.com/) with the "Desktop development with C++" workload (it includes the CMake components and Ninja);
2. No need to install OpenSSL beforehand — prebuilt x64 static libraries are committed to the repo under `third_party/openssl/` (their versions and local rebuild instructions are in [`third_party/README.md`](../../third_party/README.md); see also section 3);
3. No vcpkg / conan required: all third-party headers and libraries are committed under `third_party/`.

**Option A: open directly in VS2022 (recommended for day-to-day development)**

1. Clone the repository;
2. In VS2022, choose "Open → Local Folder" and select the repository root (VS detects the project automatically via CMakePresets.json);
3. Pick the `x64-debug` or `x64-release` preset from the configuration dropdown (Ninja generator; outputs land in `out/build/<preset-name>/`).

**Option B: command line**

```powershell
cmake --preset x64-release          # configure (Ninja, cl.exe)
cmake --build --preset x64-release  # build
```

> The command-line route must be run from the "Developer PowerShell for VS 2022" so that `cl.exe` and Ninja are on PATH.

### macOS (AppleClang)

```bash
# Dependencies: Xcode Command Line Tools + CMake/Ninja (the OpenSSL static libs are committed under third_party — no brew install needed)
xcode-select --install
brew install cmake ninja

cmake -B build -G Ninja
cmake --build build
```

The OpenSSL 3.5.9 static libraries (`libssl.a` / `libcrypto.a`) are committed per architecture under `third_party/openssl-macos-{x64,arm64}`; CMake picks the directory from `CMAKE_OSX_ARCHITECTURES` (falling back to the system architecture) and links statically. A local build therefore behaves the same as the CI-published macOS artifacts **split by architecture** (`TuPigGHD2Chinese-macos-x64` / `-macos-arm64`), both trimmed with strip + LTO (deployment target macOS 11.0).

### Linux (GCC)

```bash
sudo apt update
sudo apt install -y build-essential cmake ninja-build

cmake -B build -G Ninja
cmake --build build
```

The OpenSSL 3.5.9 static libraries (`libssl.a` / `libcrypto.a`, built with `-fPIC`) are committed under `third_party/openssl-linux-x64`; CMake finds and links them statically, so `libssl-dev` is not needed.

## 2. CMake configuration notes

| Item | Notes |
| --- | --- |
| Version macro | CI injects the version via `-DFILE_VERSION=…`; a local build defaults to `0.0.0-Dev.0` → developer build (debug logs on, self-update skipped, `--devsetver` available) |
| 64-bit guard | `CMAKE_SIZEOF_VOID_P != 8` aborts configuration; effective on both the VS `-A x64` path and the Ninja path |
| MSVC options | `/utf-8` (Chinese character set); Debug `/bigobj`; Release `/Zi` + `/DEBUG` (generates a PDB) |
| Manifest | Links `src/app.manifest` to declare a process-level UTF-8 active code page — without it, Chinese-path arguments fail to parse on non-Chinese systems |
| C++ standard | `CXX_STANDARD 20` (uses `std::optional`, `string::ends_with`, etc.) |

## 3. The OpenSSL dependency (platform differences)

| Platform | Source | Notes |
| --- | --- | --- |
| Windows | `third_party/openssl/` (the `libssl.lib` / `libcrypto.lib` + headers committed to the repo, built by the main workflow's vendor job from upstream sources) | CMake finds and links them directly, no network access needed; if the library files are missing, rebuild them via the vendor job per [`third_party/README.md`](../../third_party/README.md). `-DGHD2C_OPENSSL_ROOT=<dir>` overrides the header/library lookup location |
| macOS | `third_party/openssl-macos-{x64,arm64}` (the committed `libssl.a` / `libcrypto.a` + headers) | The directory is picked from `CMAKE_OSX_ARCHITECTURES` (falling back to the system architecture) and linked statically; if missing, restore with `git checkout -- third_party/openssl-macos-x64 third_party/openssl-macos-arm64` or rebuild via the vendor job. `-DGHD2C_OPENSSL_ROOT=<dir>` overrides |
| Linux | `third_party/openssl-linux-x64` (the committed `libssl.a` / `libcrypto.a` + headers, built with `-fPIC`) | CMake finds and links them statically (plus `CMAKE_DL_LIBS` for dlopen); if missing, restore with `git checkout -- third_party/openssl-linux-x64` or rebuild via the vendor job. `-DGHD2C_OPENSSL_ROOT=<dir>` overrides |

The third-party header-only libraries (CLI11, cpp-httplib, nlohmann/json, spdlog, WinReg) are all committed under `third_party/include/`; there is nothing to fetch.

## 4. Build outputs

| Platform | Artifact | Location |
| --- | --- | --- |
| Windows | `TuPigGHD2Chinese.exe` | `out/build/x64-release/` or `build/` |
| macOS / Linux | `TuPigGHD2Chinese` | `build/` |

> A local Windows build depends on the system VC++ runtime (Release links the CRT dynamically), matching the behavior of the published artifacts.

## 5. Common build errors

| Symptom | Cause and fix |
| --- | --- |
| `仅支持 64 位架构（x64/arm64）构建` | A 32-bit toolchain/preset was used. Pick an x64 preset in VS; add `-A x64` to the command-line configure step or use an `x64-*` preset |
| `cl.exe` not found | The command-line build was not run from a VS developer terminal; or only VS Code is installed without MSVC |
| `libssl.lib` / `libcrypto.lib` missing | `third_party/openssl` was not checked out or was deleted. Restore it with `git checkout -- third_party/openssl`; or rebuild via the main workflow's vendor job per [`third_party/README.md`](../../third_party/README.md) |
| CMake too old, complains about `cmake_minimum_required` | Upgrade to CMake ≥ 3.30 |
| macOS/Linux `libssl.a` / `libcrypto.a` missing | The bundled-library directory was deleted. Restore it with `git checkout -- third_party/openssl-macos-x64 third_party/openssl-macos-arm64 third_party/openssl-linux-x64`; or rebuild via the vendor job per [`third_party/README.md`](../../third_party/README.md) |
| Chinese comments fail to compile (MSVC) | Handled by `/utf-8`; do not remove that flag if you add compile options of your own |

## 6. Post-build verification

```powershell
# No disk writes; batch-checks mapping validity (exit code 0 = all valid)
./build/TuPigGHD2Chinese.exe --nopause dev --invalidcheck --translationfrombak

# Or run the Node tool for the same check plus untranslated-candidate extraction
cd tools/auto-maintain && npm run all
```

C++ unit tests (`version_test` / `replace_engine_test` / `selfupdate_test`, written with GoogleTest and aggregated by CTest; mandatory after touching `src/` or `tests/`):

```powershell
ctest --preset x64-release   # equivalent to ctest -C Release --output-on-failure
```

> Multi-config generator trap: on Windows, `cmake -B build` creates a VS multi-config directory by default, where a bare `ctest` without `-C Release` fake-fails with `Not Run` (#169); the preset carries the flag automatically, so prefer the preset entry point.
> GoogleTest ships with the repository (`third_party/googletest/`); nothing is downloaded at build time.

Toolchain unit tests & coverage (mandatory after touching validators or the auto-maintain tool under `tools/`):

```powershell
# Python validator tests + coverage gate (pytest collects every *-test.py under tools/ci)
python -m pip install -r tools/ci/requirements-dev.txt
python -m pytest --cov --cov-report=term-missing --cov-fail-under=90

# Node tool tests + coverage gate (Vitest; thresholds in tools/auto-maintain/vitest.config.mjs)
cd tools/auto-maintain
npm ci
npm test

# C++ coverage (on Linux; no local coverage tooling under Windows/MSVC)
cmake -B build-cov -DCMAKE_BUILD_TYPE=Debug -DCMAKE_CXX_FLAGS=--coverage -DCMAKE_EXE_LINKER_FLAGS=--coverage
cmake --build build-cov --target version_test replace_engine_test utils_test
./build-cov/version_test && ./build-cov/replace_engine_test && ./build-cov/utils_test
# Measure only this repo's tested headers; exclude third_party (vendored googletest paths also contain /src/)
gcovr --root . --filter '.*/src/utils/.*' --filter '.*/src/version/.*' --exclude '.*/third_party/.*' --txt --fail-under-line 65
```

When changing loader logic, combine this with the `main_dev` / `renderer_dev` arrays + `--devreplace` for quick verification — see the [contribution guide](贡献指南.md).

For smoke regression of loader changes, use [`tools/ci/smoke-test.ps1`](../../tools/ci/smoke-test.ps1): it auto-detects the build output and runs four test groups in turn — help, invalid arguments, localization in a temp directory, and rollback; all groups PASS means the change passes. Works under both Windows PowerShell 5.1 and pwsh 7 (#136).

## 7. Local static analysis (LSP) setup

When a local LSP/clangd keeps reporting missing third_party headers (spdlog, nlohmann/json) while checking `src/*.cpp`, it is caused by a locally missing header search path (CI builds and quality gates are unaffected). Export a compilation database to fix it at the source:

```powershell
# Export compile_commands.json during the CMake configure step (no side effects on the build)
cmake -B build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
```

Point the LSP at `build/compile_commands.json` (clangd: `--compile-commands-dir=build` or a root `.clangd` config; VS Code C/C++ extension: `C_Cpp.default.compileCommands`). The file is not committed and CI does not rely on it.
