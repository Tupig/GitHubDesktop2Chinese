# 自动维护工具（tools/auto-maintain）

**简体中文** | [English](#auto-maintain-tool-english)

`tools/auto-maintain` 是 Node.js 编写的 `localization.json` 自动维护工具，与 C++ 加载器的检测语义对齐。它**只产出报告，不直接修改** `localization.json`——所有映射改动仍需人工确认，避免正则写坏导致 GitHub Desktop 无法打开。

## 功能

| 子命令 | 功能 |
| --- | --- |
| `check` | **失效检测**：获取最新 GitHub Desktop（Windows 版），对现有映射逐条检测能否匹配到 `main.js` / `renderer.js`，找出失效项 |
| `simulate` | **依序模拟检测**：按 C++ 加载器的应用顺序（main → renderer → select）依序应用全部映射，逐条统计实际替换次数，找出「被前面正则改写抢占」导致**依序应用时**才失效的隐性条目（#207） |
| `extract` | **未翻译候选提取**：从最新 GitHub Desktop 提取尚未被现有映射覆盖的英文 UI 文案，生成可直接粘贴的 JSON 条目草稿 |
| `all` | check + extract（`npm run all` 即此；simulate 为独立子命令，需显式指定） |

## 运行环境

- Node.js ≥ 18
- 解压工具：Linux / macOS 需 `unzip`（或 `tar`）；Windows 自带 `tar`

## 用法

```bash
cd tools/auto-maintain

# 失效检测（默认读取仓库根目录 json/localization.json，与当前所在目录无关）
node src/index.js check

# 依序模拟检测（可与 check 组合）
node src/index.js simulate

# 模拟检测并输出全量逐条替换计数（默认仅输出隐性失效项）
node src/index.js simulate --verbose

# 未翻译候选提取
node src/index.js extract

# 两者都跑，并输出报告到 <workdir>/report.md
node src/index.js check extract --write-report
#   等价快捷方式：
npm run all

# 指定映射文件路径
node src/index.js check --json /path/to/localization.json

# 本地调试：复用已有 main.js/renderer.js（跳过约 307MB 下载）
node src/index.js check extract --keep-js
```

## 参数

| 参数 | 说明 |
| --- | --- |
| `check` / `simulate` / `extract` / `all` | 子命令，可组合（如 `check simulate extract`；`all` = check + extract） |
| `--json <path>` | localization.json 路径（默认按**脚本位置**推导为仓库根目录 `json/localization.json`，不受 cwd 影响） |
| `--workdir <dir>` | 下载 / 解压工作目录（默认系统临时目录） |
| `--keep-js` | 复用 workdir 中已有的 `main.js` / `renderer.js`，跳过下载 |
| `--top <n>` | extract 输出候选条数（默认 60） |
| `--verbose` | simulate 输出全量逐条替换计数（默认仅输出隐性失效项） |
| `--write-report` | 将完整报告写入 `<workdir>/report.md` |
| `--no-color` | 关闭彩色输出 |

## 工作原理

### 数据源

从 `desktop/desktop` 的最新 release 下载 `GitHubDesktop-<版本>-x64-full.nupkg`（约 **307MB**，Windows 版 Squirrel 完整包，本质是 zip）。包内 `lib/net45/resources/app/{main.js,renderer.js}` 即打包前（未 asar 压缩）的 Electron 资源，可直接读取。

**下载完整性三重校验**：

1. EOCD（zip 结束目录）签名校验；
2. 与 release 资产声明的字节数比对——尺寸不符删除断点重新下载；
3. `.part.url` 旁证文件——断点续传的 URL 与本次不一致时删除重下，防止跨版本续传拼出混合文件。

> 为什么不用 macOS 包？Windows 与 macOS 的应用文案不同（Windows 菜单带 `&` 访问键、路径相关文案为 Explorer / Command Prompt 等）。实测用 macOS 包会在 1006 条映射中产生约 **239 条假失效**。本项目的汉化目标是 **Windows 版**，检测数据源必须与之一致。

### 失效检测（check）

与 C++ 加载器的 `--invalidcheck`（`TuPigGHD2Chinese.cpp`）逻辑对齐：

- 对 `main` / `renderer` / `main_dev` / `renderer_dev` 每个条目：
  - `item[0]` 作为正则对对应 js 文本执行 `test`；
  - `item[2]`（第三项查找正则）存在时一并测试；
  - 结果分类：
    | 分类 | 含义 |
    | --- | --- |
    | `not-found` | 匹配不到（GitHub Desktop 更新后文案变了/条目写错） |
    | `regex-error` | 正则编译失败 |
    | `unsupported-syntax` | JS 侧可编译但 C++ `std::regex` 不兼容的语法（后行断言、命名捕获组、`\p{…}`、内联 flag 等）——运行时会抛错，必须修 |
    | `redos-suspect` | 命中 ReDoS 启发式（灾难性回溯风险模式）——仅告警，建议改写为更高效的等价正则；不参与失效判定 |
- 对 `select` 中 `enable: true` 的条目：按 `replaceFile` **精确等于** `main.js` / `renderer.js` 分别用对应 js 检测（与 C++ 应用侧的字面量判断一致；其他取值整条 select 不生效，跳过不计数）；
- **禁用条目不误报**（v1.2.19 起与 C++ 侧语义对齐）。

### 依序模拟检测（simulate）

`check` 只做**逐条独立**匹配，发现不了「单独能匹配、但被前面的条目先改写掉」的隐性失效。`simulate` 完整复刻 C++ 加载器的**依序应用**过程（`ProcessJsFile` + `ApplySelectForFile`），逐条统计实际替换次数：

- **模拟范围**：`main` + `renderer` + `select`（`enable: true`）全部映射，按数组内顺序依序应用——每条在**前面条目改写后的文本**上执行替换；不含 `main_dev` / `renderer_dev`（dev 模式专用数组，正常运行不加载）；
- **三元素条目**（`[查找, 替换, 条件]`）：完整复刻 C++ 的 `FillPlaceholders`——`[2]` 对**当前文本**取首个匹配、捕获组回填 `#{n}`（`$` 先转义为 `$$` 防误展开）、占位符残留则整条跳过；
- **隐性失效判定**（某条**依序应用时一次都没替换**，且满足以下全部）：
  
  | 判定条件 | 含义 |
  | --- | --- |
  | `item[0]` 对**原始未改写文本**能匹配 | 条目本身没写错（写错由 `check` 报 `not-found`） |
  | `item[2]` 不存在，或对原始文本也能匹配 | 三元素条目的条件在原始文本上成立 |
  
  满足即说明「前面有正则把它抢占/改写没了」，按原因分类输出：
  
  | 原因 | 含义 |
  | --- | --- |
  | `preempted` | 前面的条目把匹配文本改写掉了（如短条目先命中长条目的目标） |
  | `gate-miss` | 三元素条目的条件正则 `[2]` 在依序应用时匹配不到 |
  | `gate-leftover` | 三元素条目回填后 `#{n}` 占位符残留（C++ 会整条跳过） |
  
- **误报防护**：结构性跳过（空串 / `"\"\""` 哨兵、非法条目）、正则编译失败等不参与隐性判定——这些由 `check` 负责；某条在原始文本中就匹配不到（真失效）也不报——那是 `not-found` 的职责；
- `--verbose` 输出**全部**条目的逐条替换计数（`[数组#序号] 替换 N 处(独立匹配 M 处)`），零替换且原文能匹配时显示独立匹配数，便于人工核对。

### 未翻译候选提取（extract）

1. 从 `main.js` / `renderer.js` 提取双引号 / 单引号字符串字面量；
2. `isLikelyUiText()` 过滤明显非 UI 文案（内部库消息、URL、路径、错误信息、颜色值、正则、模板串、拼接碎片等）；
3. 用现有映射的**所有正则**（含 `select` 的 `replace` 项）做覆盖检测，被任一匹配到的视为「已翻译」并排除；
4. 剩余候选按出现次数排序，标注来源文件；
5. 为每个候选生成 JSON 草稿（**查找项已按字面量转义**），人工把 `【待翻译】` 替换为译文后放入对应数组。

> 提取是启发式的，会包含少量噪音（库内部提示语等）。候选用于辅助维护，专有名词可跳过。

## 报告解读

报告（`report.md`）主要区域：

- **失效表**：条目内容 + 失效分类（`not-found` / `regex-error` / `unsupported-syntax` / `redos-suspect`）+ 来源数组。处理方式：
  - `not-found`：确认 GitHub Desktop 新版文案后改写查找正则，或删除已消失功能的条目；
  - `regex-error` / `unsupported-syntax`：按[正则表达式指南](正则表达式指南.md)修正语法——这类条目会让 C++ 加载器抛异常；
  - `redos-suspect`：仅为告警，可按需改写为低回溯写法（如收敛嵌套量词），不改也不影响运行；
- **依序模拟段**（跑了 `simulate` 时）：模拟范围统计 + 隐性失效表（数组 / 序号 / 原因 / 独立匹配数 / 正则）。处理方式：
  - `preempted` / `gate-miss` / `gate-leftover`：把该条目**移到抢占它的条目之前**（更具体的在前），或改写查找正则避开前面条目的改写结果——排序规则见[映射文件格式](映射文件格式.md)；
- **候选表**：英文候选 + 出现次数 + 来源 + 可粘贴草稿。翻好 `【待翻译】` 即可入列；
- 表格行数有上限防护（超限截断），Issue 正文亦有截断兜底，避免超长报告刷屏。

## CI 自动维护

工作流：`../../.github/workflows/tupigghd2chinese.yml`（仓库唯一工作流，wiki 文档同步由其 `sync-wiki` 任务承担）。

- **触发**：每日定时（北京时间 09:23，分钟避开整点防 GitHub Actions 高负载延迟/丢弃）+ push main + 手动 `workflow_dispatch` 选择 `type=auto` 或 `type=maintain`；
- **流程**：查询 GitHub Desktop 最新版本 → 恢复缓存（安装包 + 提取结果）→ 跑 `check extract` → 渲染报告 → 创建/更新带 `auto-maintain` 标签的 Issue；
- **自动关 Issue**：失效项降为 0 时自动关闭历史维护 Issue；
- **不自动合并**：所有映射改动仍需人工确认。

缓存策略：

- 缓存 key 绑定 **GitHub Desktop 版本 + 平台 + 工具源码哈希**（`ghd-maintain-v3-<版本>-<平台>-<工具哈希>`），安装包或工具变化后自动失效重建；
- 故意**不含** `localization.json` 哈希：映射每次改动都不同，纳入会让 307MB 安装包缓存频繁失效，而报告本就在步骤内重新生成；
- 提取结果与安装包版本一致时自动复用（`.source.txt` 来源标记），跳过重复解压。

## 常见问题

- **下载 307MB 太慢/失败**：可用 `--workdir` 指定到有空间的目录；断点续传已内置，中断后重跑接着下；调试期反复用 `--keep-js` 复用已下载内容。
- **报告里的候选要不要全翻**：不用。专有名词、内部库提示可跳过，优先翻高频出现的界面文案。
- **`check` 全绿但某条翻译没生效**：大概率是被前面的正则抢占（依序应用时目标文本已被改写）。跑 `node src/index.js simulate` 找隐性失效；平时 `check` 只做逐条独立匹配，发现不了这类问题。
- **与 `--invalidcheck` 结果不一致**：两侧语义已对齐（v1.2.19），不一致通常因检测对象不同——C++ 侧默认读**本机** js（已汉化），需加 `--translationfrombak` 用干净备份；工具侧始终用**最新下载**的原始 js。

# Auto-Maintain Tool (English)

[简体中文](#自动维护工具toolsauto-maintain) | **English**

`tools/auto-maintain` is a Node.js tool that keeps `localization.json` up to date, with detection semantics aligned with the C++ loader. It **only produces reports and never modifies** `localization.json` directly — every mapping change still requires human confirmation, so a broken regex can never leave GitHub Desktop unable to open.

## What it does

| Subcommand | Function |
| --- | --- |
| `check` | **Invalid-entry detection**: fetches the latest GitHub Desktop (Windows edition) and tests every existing mapping against `main.js` / `renderer.js` to find entries that no longer match |
| `simulate` | **Sequential simulation detection**: applies all mappings in the C++ loader's order (main → renderer → select), counting actual replacements per entry, to find entries that silently stop working **only when applied in order** because an earlier regex rewrites their target first (#207) |
| `extract` | **Untranslated-candidate extraction**: pulls English UI strings from the latest GitHub Desktop that are not yet covered by existing mappings, and generates ready-to-paste JSON entry drafts |
| `all` | check + extract (`npm run all` is exactly this; simulate is a standalone subcommand and must be requested explicitly) |

## Requirements

- Node.js ≥ 18
- An unzip tool: Linux / macOS need `unzip` (or `tar`); Windows ships with `tar`

## Usage

```bash
cd tools/auto-maintain

# Invalid-entry check (reads the repo-root json/localization.json by default, regardless of cwd)
node src/index.js check

# Sequential simulation detection (combinable with check)
node src/index.js simulate

# Simulate and print per-entry replacement counts (by default only hidden failures are printed)
node src/index.js simulate --verbose

# Untranslated-candidate extraction
node src/index.js extract

# Run both and write the report to <workdir>/report.md
node src/index.js check extract --write-report
#   Equivalent shortcut:
npm run all

# Point to a specific mapping file
node src/index.js check --json /path/to/localization.json

# Local debugging: reuse existing main.js/renderer.js (skips the ~307MB download)
node src/index.js check extract --keep-js
```

## Parameters

| Parameter | Description |
| --- | --- |
| `check` / `simulate` / `extract` / `all` | Subcommands; combinable (e.g. `check simulate extract`; `all` = check + extract) |
| `--json <path>` | Path to localization.json (defaults to the repo-root `json/localization.json`, derived from the **script location** — independent of cwd) |
| `--workdir <dir>` | Download / extraction working directory (defaults to the system temp directory) |
| `--keep-js` | Reuse the `main.js` / `renderer.js` already in the workdir and skip the download |
| `--top <n>` | Number of candidates printed by extract (default 60) |
| `--verbose` | Have simulate print per-entry replacement counts (by default only hidden failures are printed) |
| `--write-report` | Write the full report to `<workdir>/report.md` |
| `--no-color` | Disable colored output |

## How it works

### Data source

It downloads `GitHubDesktop-<version>-x64-full.nupkg` (about **307MB**, the Windows Squirrel full package — essentially a zip) from the latest `desktop/desktop` release. Inside the package, `lib/net45/resources/app/{main.js,renderer.js}` are the pre-packaging (non-asar) Electron assets and can be read directly.

**Triple integrity verification of the download**:

1. EOCD (zip end-of-central-directory) signature check;
2. Byte-size comparison against the release asset — a mismatch deletes the partial download and starts over;
3. The `.part.url` sidecar file — if the URL recorded for a resumed download differs from this run's, the partial file is deleted and re-downloaded, preventing cross-version resumes from producing hybrid files.

> Why not the macOS package? Windows and macOS application copy differs (Windows menus carry `&` access keys, path-related copy mentions Explorer / Command Prompt, etc.). In practice, using the macOS package produced about **239 false invalid entries** across 1006 mappings. This project localizes the **Windows** edition, so the detection source must match it.

### Invalid-entry detection (check)

Aligned with the C++ loader's `--invalidcheck` (in `TuPigGHD2Chinese.cpp`):

- For every entry in `main` / `renderer` / `main_dev` / `renderer_dev`:
  - run `item[0]` as a regex `test` against the corresponding js text;
  - also test `item[2]` (the third-element find regex) when present;
  - result categories:
    | Category | Meaning |
    | --- | --- |
    | `not-found` | No match (the copy changed after a GitHub Desktop update, or the entry is wrong) |
    | `regex-error` | The regex fails to compile |
    | `unsupported-syntax` | Syntax that compiles in JS but is incompatible with C++ `std::regex` (lookbehind, named capture groups, `\p{…}`, inline flags, etc.) — it throws at runtime and must be fixed |
    | `redos-suspect` | Hits the ReDoS heuristic (catastrophic-backtracking risk patterns) — a warning only; rewriting to a more efficient equivalent regex is recommended, but it does not count as invalid |
- For `select` entries with `enable: true`: checked per `replaceFile` **exactly equal to** `main.js` / `renderer.js` against the corresponding js (matching the C++ side's literal comparison; any other value makes the whole select ineffective — skipped and not counted);
- **Disabled entries are never false-reported** (aligned with the C++ side since v1.2.19).

### Sequential simulation detection (simulate)

`check` only tests each entry **independently**, so it cannot see entries that "match on their own but are rewritten away by an earlier entry first". `simulate` replays the C++ loader's full **in-order application** (`ProcessJsFile` + `ApplySelectForFile`), counting the actual replacements of every entry:

- **Simulation scope**: all `main` + `renderer` + `select` (`enable: true`) mappings, applied in array order — each entry runs against the text **as rewritten by all previous entries**; `main_dev` / `renderer_dev` are excluded (dev-mode-only arrays, not loaded during normal runs);
- **Three-element entries** (`[find, replace, gate]`): fully replicate the C++ `FillPlaceholders` — `[2]` takes its first match against the **current text**, capture groups backfill `#{n}` placeholders (`$` is escaped to `$$` first to prevent accidental expansion), and any leftover placeholder skips the whole entry;
- **Hidden-failure criteria** (an entry produces **zero replacements when applied in order**, and all of the following hold):
  
  | Condition | Meaning |
  | --- | --- |
  | `item[0]` matches the **original, unrewritten text** | the entry itself is not wrong (a wrong one is reported by `check` as `not-found`) |
  | `item[2]` is absent, or also matches the original text | the gate of a three-element entry holds on the original text |
  
  When both hold, an earlier regex has "preempted" or rewritten the target away. Failures are reported by cause:
  
  | Cause | Meaning |
  | --- | --- |
  | `preempted` | an earlier entry rewrote the matching text first (e.g. a short entry consumed a longer entry's target) |
  | `gate-miss` | the gate regex `[2]` of a three-element entry no longer matches when applied in order |
  | `gate-leftover` | `#{n}` placeholders remain after backfilling (the C++ side skips the whole entry) |
  
- **False-positive protection**: structural skips (empty strings / `"\"\""` sentinels, invalid entries), regex compile failures, etc. never count as hidden — `check` owns those; an entry that fails to match even the original text (a true invalid) is not reported either — that is `not-found`'s job;
- `--verbose` prints per-entry replacement counts for **every** entry (`[array#index] replaced N (standalone M)`), showing the standalone match count for zero-replacement entries that still match the original text, for manual verification.

### Untranslated-candidate extraction (extract)

1. Extract double-quoted / single-quoted string literals from `main.js` / `renderer.js`;
2. `isLikelyUiText()` filters out text that is clearly not UI copy (internal library messages, URLs, paths, error messages, color values, regexes, template strings, concatenation fragments, etc.);
3. Coverage detection runs **all** existing mapping regexes (including the `replace` items of `select` entries); anything matched is treated as "already translated" and excluded;
4. The remaining candidates are sorted by occurrence count and tagged with their source file;
5. A JSON draft is generated for each candidate (**find patterns already escaped as literals**); a human replaces `【待翻译】` with the translation and puts the entry into the corresponding array.

> Extraction is heuristic and includes some noise (internal library prompts, etc.). Candidates are a maintenance aid; proper nouns can be skipped.

## Reading the report

The report (`report.md`) has these main areas:

- **Invalid table**: entry content + category (`not-found` / `regex-error` / `unsupported-syntax` / `redos-suspect`) + source array. How to handle:
  - `not-found`: confirm the new GitHub Desktop copy, rewrite the find regex, or delete entries for features that no longer exist;
  - `regex-error` / `unsupported-syntax`: fix the syntax per the [regular expression guide](正则表达式指南.md) — such entries make the C++ loader throw;
  - `redos-suspect`: a warning only; optionally rewrite to a low-backtracking form (e.g. tighten nested quantifiers) — leaving it as-is does not affect runtime;
- **Sequential simulation section** (present when `simulate` ran): scope statistics + a hidden-failure table (array / index / cause / standalone matches / regex). How to handle:
  - `preempted` / `gate-miss` / `gate-leftover`: move the entry **before** the one that preempts it (more specific entries first), or rewrite the find regex so it does not collide with earlier rewrites — see the ordering rules in [Localization File Format](映射文件格式.md);
- **Candidates table**: English candidates + occurrence count + source + paste-ready drafts. Translate the `【待翻译】` placeholders and they are ready to go in;
- Table row counts are capped (truncated beyond the limit), and the Issue body has a further truncation backstop, so oversized reports never flood the page.

## CI auto-maintenance

Workflow: `../../.github/workflows/tupigghd2chinese.yml` (the repository's single workflow; its `sync-wiki` job also handles wiki documentation sync).

- **Triggers**: daily schedule (09:23 Beijing time — the off-round minute avoids GitHub Actions high-load delays/drops) + push to main + manual `workflow_dispatch` with `type=auto` or `type=maintain`;
- **Flow**: query the latest GitHub Desktop version → restore caches (installer + extraction results) → run `check extract` → render the report → create/update the Issue labeled `auto-maintain`;
- **Auto-closing Issues**: historical maintenance Issues are closed automatically when the invalid count drops to 0;
- **No auto-merge**: every mapping change still requires human confirmation.

Cache strategy:

- The cache key binds the **GitHub Desktop version + platform + tool-source hash** (`ghd-maintain-v3-<version>-<platform>-<tool-hash>`); a changed installer or tool invalidates and rebuilds it automatically;
- It deliberately **excludes** the `localization.json` hash: mappings change all the time, and including it would keep invalidating the 307MB installer cache, while the report is regenerated within the job anyway;
- Extraction results are reused automatically when they match the installer version (the `.source.txt` source marker), skipping redundant extraction.

## FAQ

- **The 307MB download is slow or fails**: point `--workdir` at a directory with space; resumable downloads are built in — just re-run after an interruption; use `--keep-js` repeatedly during debugging to reuse downloaded content.
- **Should every candidate in the report be translated?**: No. Skip proper nouns and internal library prompts; prioritize high-frequency UI copy.
- **`check` is all green but a translation never applies**: it was most likely preempted — an earlier regex rewrote its target before it ran. Run `node src/index.js simulate` to find hidden failures; plain `check` only tests entries independently and cannot see this class of problems.
- **Results differ from `--invalidcheck`**: the two sides are semantically aligned (since v1.2.19); differences usually come from different detection targets — the C++ side reads the **local** js by default (already localized), so add `--translationfrombak` to use the clean backup, while the tool always uses the freshly downloaded original js.
