# 贡献指南

欢迎为 GitHubDesktop2Chinese 贡献翻译、修复与改进！本文覆盖从克隆到 PR 的完整流程。日常翻译贡献**不需要**编译环境，改一个 JSON 文件即可。

> 先读必读材料：
> - [映射文件格式](映射文件格式.md) —— 条目长什么样、放哪个数组
> - [正则表达式指南](正则表达式指南.md) —— 转义规则与 `std::regex` 黑名单（避免「匹配不到」或「写坏 GitHub Desktop」）

## TL;DR

```bash
git clone https://github.com/<你的用户名>/GitHubDesktop2Chinese.git
# 编辑 json/localization.json
#   新条目先放 main_dev / renderer_dev 验证（见下）
#   验证通过后移入 main / renderer（注意「短含长」排序）
git checkout -b fix/translate-xxx
git commit -am "补充 xx 模块 N 条翻译"
git push -u origin fix/translate-xxx
# 到 GitHub 上开 PR（目标分支 main）
```

## 1. 找活儿

- **失效条目**：每日 CI 自动检测并在 `auto-maintain` 标签的 Issue 中报告（[Issue 列表](https://github.com/Tupig/GitHubDesktop2Chinese/issues)），认领后修复对应条目即可；
- **未翻译候选**：同一 Issue 的报告中带「可直接粘贴的条目草稿」，把 `【待翻译】` 换成中文即可；
- 也可以自己跑工具生成最新报告（见第 3 节）。

## 2. 补充翻译

### 2.1 用自动维护工具生成草稿（推荐）

```bash
cd tools/auto-maintain
npm run all
```

- 需要 Node.js ≥ 18；
- 报告写入系统临时目录 `ghdesktop-auto-maintain/report.md`；
- 按报告的「来源」列把条目放入 `main`（main.js）或 `renderer`（renderer.js）数组；
- 草稿的查找项已按字面量转义好，只需把 `【待翻译】` 替换为中文译文；
- 工具详情见[自动维护工具](自动维护工具.md)。

### 2.2 手写条目

在 `json/localization.json` 对应数组中按格式追加：

```json
["\"&Repository\"", "\"存储库(&R)\""]
```

规则速记：

- 匹配的双引号用 `\"` 转义；正则特殊字符用**双反斜杠**（如 `\\(`）；替换项是为正则加的反斜杠一律**不要**；
- 查找项建议带引号边界，避免误匹配长文本；
- **条目顺序**：一般追加到数组末尾；若与已有条目「短含长」（新条目是已有条目的子串或超集），必须把更具体的条目插到更宽泛条目**之前**；
- 译文问号用全角 `？`，末尾不留空格；
- JSON 数组最后一项结尾不能有逗号。

## 3. 本地验证（提交前必做至少一项）

### 方式 A：快速验证新条目（推荐）

1. 把新条目放进 `main_dev` / `renderer_dev`（而不是正式数组）；
2. 运行加载器并按住 `Shift`（或加 `dev -d`）进入开发者选项，开启「**仅替换指定映射项**」（菜单项 6）；
3. 只替换 dev 数组，秒级完成，打开 GitHub Desktop 查看效果；
4. 验证通过后把条目**移动**到 `main` / `renderer`（遵守排序规则）再提交。

### 方式 B：批量自检失效条目

需要本机已装 GitHub Desktop（或用 `-g` 指定 js 目录）：

```powershell
GitHubDesktop2Chinese.exe --nopause dev --invalidcheck --translationfrombak
```

- `--nopause` 是程序级参数，必须写在 `dev` **之前**；
- 退出码 = 失效条数，`0` 为全部有效；
- 输出会逐条报告 `[main] / [renderer] / [select …] 检测到失效项` 与正则编译错误。

### 方式 C：Node 自动维护工具（无需安装 GitHub Desktop）

```bash
cd tools/auto-maintain && npm run all
```

与 C++ 侧 `--invalidcheck` 语义对齐（含 `std::regex` 不兼容语法检测），顺带输出未翻译候选。

> PR 会自动触发 CI 的 **JSON 质量校验**（正则合法性、结构完整性、占位符检查、`std::regex` 黑名单、译文问句全角、条目顺序告警）与**工具自检**，本地过了 CI 一般也过。

## 4. 发布说明（docs/ReleaseBody.md）

`json/`、`src/`、`third_party/`、`CMakeLists.txt`、`CMakePresets.json` 任一变更都会在 push main / 每日定时 / 手动 `auto` 时**自动发布新版本**（补丁号 +1）。CI 发布时从 `docs/ReleaseBody.md` 提取变更行拼进 Release 说明，规则：

- 在「版本更新日志」区域追加一行变更描述；
- 行尾标注**下一个发布版本**的**全角**括号标记，如 `（v1.2.25）`；
  - 查当前最新 tag：`git tag --sort=-v:refname | head -1`，版本号 +1 即下一个版本；
- 未标注或版本号未命中的行不会出现在任何 Release 中，也**不阻断**发布（说明显示「未找到变更记录」）；
- 静态的「### 程序说明」段落每次发布自动附带，无需逐版维护。

示例（当前最新 tag 为 v1.2.24 时）：

```markdown
- 补充 警告对话框模块 5 条翻译，修复 2 条失效条目（v1.2.25）
```

## 5. 改加载器代码（C++）

1. 按[编译指南](编译指南.md)搭好环境；
2. 本地构建默认是 `0.0.0-Dev` 开发者版本：debug 日志全开、跳过自更新检查；
3. 调试 `minversion` 逻辑可用 `--devsetver` 指定任意版本；
4. 自测重点场景：
   - `--nopause` 管道/重定向运行不挂起；
   - 中文路径（GBK 控制台）下 `-g` / `-j` / 交互输入不乱码；
   - 断网、映射损坏时回滚 `--rollback` 仍可用（回滚在 json 加载之前短路）；
5. 提交 PR，CI 会跑多平台构建 + 产物功能测试 + CodeQL。

## 6. PR 检查清单

- [ ] 新条目已从 `_dev` 数组移入正式数组（如走方式 A）；
- [ ] 「短含长」条目相对顺序正确；
- [ ] `--invalidcheck` 退出码为 0（或 CI 质量门通过）；
- [ ] 译文问号全角、末尾无空格、术语与现有翻译一致；
- [ ] `docs/ReleaseBody.md` 已追加带全角版本标记的变更行；
- [ ] PR 目标分支为 `main`。
