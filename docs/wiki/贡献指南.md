# 贡献指南

**简体中文** | [English](#contribution-guide-english)

欢迎为 GitHubDesktop2Chinese 贡献翻译、修复与改进！本文覆盖从克隆到 PR 的完整流程。日常翻译贡献**不需要**编译环境，改一个 JSON 文件即可。

> 先读必读材料：
> - [映射文件格式](映射文件格式.md) —— 条目长什么样、放哪个数组
> - [正则表达式指南](正则表达式指南.md) —— 转义规则与 `std::regex` 黑名单（避免「匹配不到」或「写坏 GitHub Desktop」）

## TL;DR

```bash
git clone https://github.com/<你的用户名>/GitHubDesktop2Chinese.git
# 编辑 json/localization.json
#   新条目先放 main_dev / renderer_dev 验证（见下）
#   验证通过后移入 main / renderer（注意「短含长」排序）
git checkout -b fix/translate-xxx
git commit -am "补充 xx 模块 N 条翻译"
git push -u origin fix/translate-xxx
# 到 GitHub 上开 PR（目标分支 main）
```

## 1. 找活儿

- **失效条目**：每日 CI 自动检测并在 `auto-maintain` 标签的 Issue 中报告（[Issue 列表](https://github.com/Tupig/GitHubDesktop2Chinese/issues)），认领后修复对应条目即可；
- **未翻译候选**：同一 Issue 的报告中带「可直接粘贴的条目草稿」，把 `【待翻译】` 换成中文即可；
- 也可以自己跑工具生成最新报告（见第 3 节）。

## 2. 补充翻译

### 2.1 用自动维护工具生成草稿（推荐）

```bash
cd tools/auto-maintain
npm run all
```

- 需要 Node.js ≥ 18；
- 报告写入系统临时目录 `ghdesktop-auto-maintain/report.md`；
- 按报告的「来源」列把条目放入 `main`（main.js）或 `renderer`（renderer.js）数组；
- 草稿的查找项已按字面量转义好，只需把 `【待翻译】` 替换为中文译文；
- 工具详情见[自动维护工具](自动维护工具.md)。

### 2.2 手写条目

在 `json/localization.json` 对应数组中按格式追加：

```json
["\"&Repository\"", "\"存储库(&R)\""]
```

规则速记：

- 匹配的双引号用 `\"` 转义；正则特殊字符用**双反斜杠**（如 `\\(`）；替换项是为正则加的反斜杠一律**不要**；
- 查找项建议带引号边界，避免误匹配长文本；
- **条目顺序**：一般追加到数组末尾；若与已有条目「短含长」（新条目是已有条目的子串或超集），必须把更具体的条目插到更宽泛条目**之前**；
- 译文问号用全角 `？`，末尾不留空格；
- JSON 数组最后一项结尾不能有逗号。

## 3. 本地验证（提交前必做至少一项）

### 方式 A：快速验证新条目（推荐）

1. 把新条目放进 `main_dev` / `renderer_dev`（而不是正式数组）；
2. 运行加载器并按住 `Shift`（或加 `dev -d`）进入开发者选项，开启「**仅替换指定映射项**」（菜单项 6）；
3. 只替换 dev 数组，秒级完成，打开 GitHub Desktop 查看效果；
4. 验证通过后把条目**移动**到 `main` / `renderer`（遵守排序规则）再提交。

### 方式 B：批量自检失效条目

需要本机已装 GitHub Desktop（或用 `-g` 指定 js 目录）：

```powershell
GitHubDesktop2Chinese.exe --nopause dev --invalidcheck --translationfrombak
```

- `--nopause` 是程序级参数，必须写在 `dev` **之前**；
- 退出码 = 失效条数，`0` 为全部有效；
- 输出会逐条报告 `[main] / [renderer] / [select …] 检测到失效项` 与正则编译错误。

### 方式 C：Node 自动维护工具（无需安装 GitHub Desktop）

```bash
cd tools/auto-maintain && npm run all
```

与 C++ 侧 `--invalidcheck` 语义对齐（含 `std::regex` 不兼容语法检测），顺带输出未翻译候选。

> PR 会自动触发 CI 的 **JSON 质量校验**（正则合法性、结构完整性、占位符检查、`std::regex` 黑名单、译文问句全角、条目顺序告警）与**工具自检**，本地过了 CI 一般也过。

## 4. 发布说明（docs/ReleaseBody.md）

`json/`、`src/`、`third_party/`（不含纯文档 `third_party/README.md`）、`CMakeLists.txt`、`CMakePresets.json` 任一变更都会在 push main / 每日定时 / 手动 `auto` 时**自动发布新版本**（版本号按进位规则自动递增）。CI 发布时从 `docs/ReleaseBody.md` 提取变更行拼进 Release 说明，规则：

- 在「版本更新日志」区域追加一行中文变更描述，并在下一行缩进追加对应英文翻译；
- 两行行尾均标注**下一个发布版本**的**全角**括号标记，如 `（v0.0.2）`；
  - 查当前最新 tag：`git tag --sort=-v:refname | head -1`，按进位规则递增即下一个版本（patch +1，满 100 进位 minor 并重置为 1）；
- 未标注或版本号未命中的行不会出现在任何 Release 中，也**不阻断**发布（说明显示「未找到变更记录」）；
- 静态的「### 程序说明」段落每次发布自动附带，无需逐版维护。

示例（当前最新 tag 为 v0.0.1 时）：

```markdown
- 补充 警告对话框模块 5 条翻译，修复 2 条失效条目（v0.0.2）
  - Added 5 translations for the warning-dialog module and fixed 2 invalid entries（v0.0.2）
```

## 5. 改加载器代码（C++）

1. 按[编译指南](编译指南.md)搭好环境；
2. 本地构建默认是 `0.0.0-Dev` 开发者版本：debug 日志全开、跳过自更新检查；
3. 调试 `minversion` 逻辑可用 `--devsetver` 指定任意版本；
4. 自测重点场景：
   - `--nopause` 管道/重定向运行不挂起；
   - 中文路径（GBK 控制台）下 `-g` / `-j` / 交互输入不乱码；
   - 断网、映射损坏时回滚 `--rollback` 仍可用（回滚在 json 加载之前短路）；
5. 提交 PR，CI 会跑多平台构建 + 产物功能测试 + CodeQL。

## 6. PR 检查清单

- [ ] 新条目已从 `_dev` 数组移入正式数组（如走方式 A）；
- [ ] 「短含长」条目相对顺序正确；
- [ ] `--invalidcheck` 退出码为 0（或 CI 质量门通过）；
- [ ] 译文问号全角、末尾无空格、术语与现有翻译一致；
- [ ] `docs/ReleaseBody.md` 已追加带全角版本标记的变更行；
- [ ] PR 目标分支为 `main`。

## 7. 行为准则与安全

- 交流请保持友善，遵守[行为准则](../../.github/CODE_OF_CONDUCT.md)；
- 安全漏洞**不要**开 Issue 或 PR 公开讨论，走[私密漏洞报告](../../SECURITY.md)。

# Contribution Guide (English)

[简体中文](#贡献指南) | **English**

Welcome to contribute translations, fixes and improvements to GitHubDesktop2Chinese! This page covers the full flow from cloning to PR. Day-to-day translation contributions do **not** require a build environment — editing a single JSON file is enough.

> Required reading first:
> - [Mapping file format](映射文件格式.md) — what an entry looks like and which array it belongs to
> - [Regular expression guide](正则表达式指南.md) — escaping rules and the `std::regex` blacklist (to avoid "pattern does not match" failures or breaking GitHub Desktop)

## TL;DR

```bash
git clone https://github.com/<your-username>/GitHubDesktop2Chinese.git
# Edit json/localization.json
#   Put new entries into main_dev / renderer_dev first for verification (see below)
#   After verification, move them into main / renderer (mind the "short-in-long" ordering)
git checkout -b fix/translate-xxx
git commit -am "补充 xx 模块 N 条翻译"
git push -u origin fix/translate-xxx
# Open a PR on GitHub (target branch: main)
```

## 1. Finding work

- **Invalid entries**: detected daily by CI and reported in Issues labeled `auto-maintain` ([issue list](https://github.com/Tupig/GitHubDesktop2Chinese/issues)); claim one and fix the corresponding entries;
- **Untranslated candidates**: the same report contains "ready-to-paste entry drafts" — just replace `【待翻译】` with the Chinese translation;
- You can also run the tool yourself to generate a fresh report (see section 3).

## 2. Adding translations

### 2.1 Generate drafts with the auto-maintain tool (recommended)

```bash
cd tools/auto-maintain
npm run all
```

- Requires Node.js ≥ 18;
- The report is written to `ghdesktop-auto-maintain/report.md` in the system temp directory;
- Following the report's "source" column, put the entries into the `main` (main.js) or `renderer` (renderer.js) array;
- The find patterns in the drafts are already escaped as literals — just replace `【待翻译】` with the Chinese translation;
- See the [auto-maintain tool](自动维护工具.md) page for tool details.

### 2.2 Writing entries by hand

Append entries to the corresponding array of `json/localization.json`, following the format:

```json
["\"&Repository\"", "\"存储库(&R)\""]
```

Quick rules:

- Escape matched double quotes with `\"`; escape regex special characters with **double backslashes** (e.g. `\\(`); backslashes added for the regex must **never** appear in the replacement;
- Find patterns should include quote boundaries to avoid accidentally matching longer texts;
- **Entry order**: entries usually go at the end of the array; if a new entry is "short-in-long" with an existing one (a substring of it or a superset), the more specific entry must be inserted **before** the broader one;
- Use the full-width `？` for question marks in translations; no trailing spaces;
- The last item of a JSON array must not be followed by a comma.

## 3. Verifying locally (do at least one before submitting)

### Option A: quick check of new entries (recommended)

1. Put the new entries into `main_dev` / `renderer_dev` (not the official arrays);
2. Run the loader and hold `Shift` (or add `dev -d`) to open the developer options, then enable "**replace only specified mappings**" (menu item 6);
3. Only the dev arrays are replaced, which finishes in seconds — open GitHub Desktop to see the effect;
4. After verification, **move** the entries into `main` / `renderer` (respecting the ordering rules) before committing.

### Option B: batch self-check for invalid entries

Requires GitHub Desktop installed locally (or pass its js directory via `-g`):

```powershell
GitHubDesktop2Chinese.exe --nopause dev --invalidcheck --translationfrombak
```

- `--nopause` is a program-level flag and must come **before** `dev`;
- The exit code equals the number of invalid entries; `0` means all valid;
- The output reports each `[main] / [renderer] / [select …] 检测到失效项` line and regex compilation errors.

### Option C: the Node auto-maintain tool (no GitHub Desktop installation needed)

```bash
cd tools/auto-maintain && npm run all
```

Semantics are aligned with the C++ `--invalidcheck` (including detection of syntax unsupported by `std::regex`), and it also outputs untranslated candidates.

> PRs automatically trigger CI's **JSON quality checks** (regex validity, structural integrity, placeholder checks, the `std::regex` blacklist, full-width question marks in translated questions, entry-order warnings) and the **tool self-test**; if it passes locally, it generally passes CI.

## 4. Release notes (docs/ReleaseBody.md)

Any change to `json/`, `src/`, `third_party/` (excluding the docs-only `third_party/README.md`), `CMakeLists.txt` or `CMakePresets.json` automatically publishes a new version (the version auto-increments per the carry rule) on push to main, on the daily schedule, or on manual `auto`. When publishing, CI extracts the change lines from `docs/ReleaseBody.md` into the release notes. Rules:

- Append a Chinese change-description line to the "版本更新日志 / Changelog" section, and an indented English translation line right below it;
- Both lines end with the **full-width** version marker of the **next release version**, e.g. `（v0.0.2）`;
  - Check the current latest tag with `git tag --sort=-v:refname | head -1`, then increment per the carry rule (patch +1, carrying into minor at 100 and resetting to 1);
- Lines without a marker, or whose version does not match the release, never appear in any release and never block publishing (the notes show a "no change record found" notice instead);
- The static "### 程序说明" section is attached to every release automatically; no per-version maintenance is needed.

Example (when the current latest tag is v0.0.1):

```markdown
- 补充 警告对话框模块 5 条翻译，修复 2 条失效条目（v0.0.2）
  - Added 5 translations for the warning-dialog module and fixed 2 invalid entries（v0.0.2）
```

## 5. Changing the loader code (C++)

1. Set up the environment per the [build guide](编译指南.md);
2. A local build is a `0.0.0-Dev` developer build by default: all debug logs enabled, self-update check skipped;
3. Use `--devsetver` to exercise the `minversion` logic with an arbitrary version;
4. Focus your self-tests on:
   - `--nopause` does not hang when piped or redirected;
   - no mojibake with Chinese paths (GBK console) for `-g` / `-j` and interactive input;
   - `--rollback` still works offline or with a corrupted mapping (rollback short-circuits before json loading);
5. Submit the PR; CI runs multi-platform builds + artifact functional tests + CodeQL.

## 6. PR checklist

- [ ] New entries moved from the `_dev` arrays into the official arrays (if you used Option A);
- [ ] "Short-in-long" entries are in the correct relative order;
- [ ] `--invalidcheck` exits 0 (or the CI quality gate passes);
- [ ] Translations use full-width question marks, no trailing spaces, and terminology consistent with existing translations;
- [ ] `docs/ReleaseBody.md` has the new change lines with the full-width version marker;
- [ ] The PR targets `main`.

## 7. Code of conduct and security

- Please keep discussions friendly and follow the [Code of Conduct](../../.github/CODE_OF_CONDUCT.md);
- Do **not** discuss security vulnerabilities in public Issues or PRs — use [private vulnerability reporting](../../SECURITY.md) instead.
